今天几乎整天都在和 DanceTrack 上的复现差距较劲：同一个 test 集，论文的 PlugTrack＋DiffMOT 能到 63.3 HOTA，我的原版配置只有 61.34，中间差了近 2 分。为了搞清楚这 2 分是怎么丢的，我从资产核对一路查到单帧关联日志，中间推翻过自己两个结论。

## 先把 1.96 分拆开：问题在身份关联，不在检测

第一件事是确认差距的"形状"。把指标摊开看，DetA 只差 0.119，但 AssA 差 2.6、IDF1 差 2.5——说明检测框一直都在，问题出在"持续把同一个人接成同一条轨迹"上。截图里的 `Ours(DiffMOT)` 也确认了对应关系，括号中的 +1.0 是它相对纯 DiffMOT 的提升，跟我新加的固定校准不是同一个比较对象。

补跑官方纯 DiffMOT 基线后，分差能拆成两段：纯 DiffMOT 本机 61.867，论文 62.3，差 **0.433**；而加入 PlugTrack 后，论文涨 1.0，我这边反而跌 0.527。也就是说 1.96 分里，1.527 分来自 PlugTrack 这一层的增益方向反了。这一步至少把"是不是检测输入或环境的问题"排除了大半。

## 资产核对：检测器和权重都没用错

顺着"检测输入"这条线，我把用到的资产逐个对了一遍。检测走的是官方发布的预计算 YOLOX-X 结果包，跟我本地下载的那份逐字节哈希一致；官方 release 里的 YOLOX-X 权重，也和我手里那份 793MB 的文件哈希完全相同，只是当初从镜像拿的。跟踪用的运动权重是官方 `DanceTrack_official.pt`，严格加载 208 个张量无缺无余。ReID 用的是官方预计算特征。

结论是：**没有误用自己训练的 YOLOX 权重**。不过我也把话说得更严谨了一些——"来源一致、型号一致"不等于"用该权重重新推理能逐项复现出这份检测文件"，这一条当时还没有验证。

## 逐帧定位：融合框把一条 lost 轨迹挤掉了

真正有信息量的是单序列对照。我选 `dancetrack0003`，同一 seed、同一检测和 ReID 输入，跑纯 DiffMOT 和接入 PlugTrack 的 E2。前 144 帧两者完全一致；第 145 帧轨迹池变成 11 条 vs 10 条；第 146 帧纯 DiffMOT 重新激活了 ID 12、13 两条，E2 只能激活 ID 12，另外新建了一条。

再往下钻，找到了具体机制：第 144 帧时，active 的 ID 9 与 lost 的 ID 13 之间，纯 DiffMOT 的 IoU 是 0.8285，PlugTrack 的融合框把它抬到 0.9352——刚好跨过 DiffMOT 内置的 `IoU > 0.85` 去重阈值，于是 ID 13 被 `remove_duplicate_stracks` 提前清理。我做了因果对照：PlugTrack 不动，只临时关掉去重，ID 13 就保住了，第 146 帧也正常重新激活。

## 但"接入有 bug"这个结论，我说早了

拿到上面的机制后我一度下了个偏重的判断，随后自我评估时又收回来了，这一步挺关键：

- **已确认**：E2 在第 144 帧通过去重剔除了 ID 13；关掉去重后它会被重新激活。
- **未证明**：这个剔除本身是"错的"——那需要真实身份标注才能判。
- **未证明**：这个局部机制能解释整个 test 集的下降，我只查了一条序列的一小段。

而且"融合改变预测框 → 改变关联和去重 → 改变轨迹生命周期"，本来就是这类方法的正常效应。要认定是接入 bug，得证明本地实现违反了官方接口或时序。

于是我做了前向等价性对齐：用真实历史窗口，在第 144、145、146 帧逐项比较官方示例的独立转写与本地融合层，`bbox_mp`、KF、融合框、不确定性全部 `max_abs_error = 0.0`，也没发现归一化、五帧补齐、residual 转换之类的错误。坐标转换的闭环误差同样为 0，不存在"重复加当前坐标"的问题。**前向数学是干净的，变化发生在它之后的生命周期处理上。**

## 另一条线：复现度排查与那个检测预处理的坑

另一头同时在推进整体复现度。val 上 Phase 1 已经跑出 HOTA 58.91，换 seed 是 58.8353，另一个发现是带 events 与不带 events 的结果完全一致，证明了事件记录是输出中性的。

比较有价值的坑是检测预处理。DiffMOT 仓库里那套 `ValTransform`／`preproc` 实际不做归一化，直接吃 0–255 原值；但单帧探针一跑就露馅了——只有走归一化预处理，才能对上官方检测包：分数是 `obj_conf × class_conf`，第 2 行 0.8760163 对官方 0.8760161，框差不超过 0.6px。用无归一化的那条路径，会产出上百个乱框。也就是说，官方 dump 检测时用的并不是仓库里那条 ValTransform 路径。

全量 25 序列比对的结果让人安心：匹配率 99.83%，96.6% 的帧数量完全一致。少量离群值都落在 0.01 置信度地板附近的垃圾框上，而跟踪器实际只消费 ≥0.4 的框——按这个带宽重新分层统计，匹配率是 99.93–99.99%，三个最差序列合计只有 5 个未匹配框。

test 侧官方纯 DiffMOT 已经跑完 35/35 序列，打包好了提交包，本地没有 test GT，只能上评测服务器算分。

## 接下来怎么走

下一步我打算先做"接入等价性检查"，而不是继续调参：让接入 PlugTrack 的版本**直接旁路融合、返回原始 MP 预测**，看逐帧预测、关联和轨迹输出是否与纯 DiffMOT 完全一致。只把某个系数设成零不够稳，可能仍会触发权重截断或额外随机数消耗。先拿 0004、0019 这两条已知负收益序列小规模验证，再扩到完整 val。

现在最需要的产物是**一份"首次分叉证据"**，而不是又一个总分——它才能告诉我该修代码、修配置，还是重新设计融合。

## 今日要点

- test 集 1.96 分差距可拆为：纯 DiffMOT 基线差 0.433 ＋ PlugTrack 增量方向反了 1.527；损失集中在 AssA／IDF1，检测层面基本无差。
- 检测与权重资产已排除嫌疑：官方预计算检测包、YOLOX-X 权重、运动权重、ReID 特征来源与哈希均一致。
- 已定位到一个可信的局部分叉机制：融合框把 IoU 从 0.8285 推到 0.9352，跨过 0.85 去重阈值，导致一条 lost 轨迹被提前清理，后续轨迹池逐步分叉。
- 前向接入的数学已验证等价（逐项误差为 0），所以别急着叫它 bug；它能否解释全 test 下降，证据还不够。
- 下一步做接入等价性检查（旁路融合直返原始预测），先跑 0004／0019，目标是拿出首次分叉证据。
