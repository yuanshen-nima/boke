今天基本上一整天都在做同一件事：给 MM-Tracker 和 OC-SORT 的集成研究搭一个真正能跑通、也能撑起论文的项目。上午还在讨论目录结构和依赖可行性，晚上已经在修正位移单位造成的指标偏差，最后又把整个实验架构从 Windows 原生切到了 WSL2。中间推翻过两次结论，好在每次推翻都留下了可复现的证据。

## 给 plugMMTracker 立项：先把"论文能不能写"当成需求

我一开始就提了句很实在的话——在这个目录下建项目，可视化数据必须做好，不然论文不好写。这句话后来变成了整个项目的硬约束：训练评估指标、轨迹可视化、论文制图的数据导出，全都被当成一等功能来设计，而不是事后补。

现状梳理花了不少时间。本地已经有一份可用的 MM-Tracker 基线、Motion Mamba 权重和 VisDrone 数据，目标目录还是空的。所以没必要去网上盲拉一个版本——那样实验根本没法复现。定了"冻结本地基线 + 模块化旁路接入"的路线：predictors、fusion、association、lifecycle、diagnostics、evaluation、visualization 各自独立，A0 到 A4 用配置隔离，不去原来那个近千行的 tracker 文件里继续堆逻辑。

后端选型是最关键的一次决策。原项目依赖 `mamba_ssm` 和一堆自定义 CUDA 扩展，而我这台机器是 Windows。三个方案摆在面前：Windows 原生兼容层、WSL2 跑原版、先导出 ONNX 再推理。最后选了第一个——用纯 PyTorch 实现 Mamba 的 selective scan 和 correlation 替代实现，直接加载现有权重，速度慢一点但当前环境真能跑起来，而且后端会明确标记为参考实现，绝不伪装成原生 CUDA。

## 数据与可视化：先想清楚每张图要证明什么

可视化这块我没有从"记什么日志"出发，而是反着来：先明确每张论文图要支撑什么结论，再倒推需要哪些字段。核心原则是在线推理只记录可部署的信息，GT 只能在离线审计阶段追加，避免未来信息泄漏。

每次实验落成独立目录，包含配置快照、整体与分序列指标、预测/匹配/重激活事件、每张图对应的干净源数据、多格式图件、典型案例素材和一个本地交互审计页。事件字段拆成 Prediction 和 Assignment 两组——预测框、三者 IoU、alpha、不确定度、原始代价与 OCM 代价、候选数、OCM 是否改变匹配等等。后面事实证明，正是这套在线事件记录，才让单位换算的错误能被定位出来。

## 规范评审：接受什么、拒绝什么

设计规范写完提交后，我拿到了一份很长的外部评审。我把它当建议而不是指令，逐条核对：接受的是能提高归因可信度的部分——几处定义缺口、固定检测缓存、四态 OCM 审计、在线与离线尺度字段分离，以及"先验证可行性、再谈出版流水线"。

不接受的是"没拿到 Linux 参考输出就不许开始写代码"这个隐含前提。本机没有可用的 WSL，如果按这个要求走，项目会原地冻结好几周。我把它改成了一条可执行的边界：Windows 版本先标为 `A0-W`，允许实现和本机验证，但只有过了跨平台一致性门槛之后，才能称为原始 A0 并用于正式归因。规范出到 V1.1，这个"命名纪律"后来救了我一次。

## Windows 上的真实闭环：两个必须记录的坑

实现阶段最有价值的部分不是顺利，而是被数据打脸。

一是权重加载。按原权重的 118 个键和形状原样复建 Mamba 与 Motion Mamba，严格要求缺键多键都直接失败，最终 118/118 全部对上，CPU 和 GPU 前向都跑通。

二是缓存链路。为了后续 alpha 扫描的输入逐字节一致，我把检测和运动场做成一次性缓存，完整 184 帧只花了 22 秒，产出二十多万条检测和 184 个真实运动场，都带哈希清单。重放阶段只读缓存，不再重复检测。

中途还被数据纠正过两处协议问题：原多类别跟踪器的 track_id 是类内唯一，所以事件主键必须加上类别；单序列做 bootstrap 区间会退化成一个点，不能假装是有效置信区间，图上明确标注为 pilot、CI 不可用。另外封存运行加了禁止覆盖保护，图表后端固定为无界面可复现的模式。

## 单序列 pilot 的结果，以及它不能说明的事

第一版跑出来 HOTA 66.25，看着还不错。但独立审查抓到一个实质问题：Motion Mamba 输出的是低分辨率网格位移，我直接当像素位移用了，少乘了约 14 倍的宽高比例。这组指标和配图全部作废，两套调试产物被废弃删除。

修正之后再跑：A0-W 的 HOTA 67.32、IDF1 79.40、MOTA 63.89、IDSW 8；三千八百多个有效预测事件里，卡尔曼滤波胜出 35.14%、Motion Mamba 胜出 39.30%、并列 25.56%，oracle 相对 Mamba 只高 1.97 个百分点。而 A1 的所有正 alpha 都没有提升 HOTA 和 IDF1，所以当前决策是"结论不明"，不启动后续阶段。这是单序列的工程 pilot，不能当成完整验证集的论文结论。

二次审查又指出两处"宣称强于实际检查"的地方——端点的 assignment 一致性没有真正做配对比较，CSV 到决策的链条没有逐级哈希绑定。补齐后拿到"可以交付"的结论，最终留下唯一一套修正后的密封结果。

## 架构转向：把主战场搬到 WSL2

真正让我重新想架构的是 A0 冻结问题。跨平台等价性要分三层验证：算子、Motion Mamba 预测框、最终跟踪结果。验证器都写好了，但没有 Linux 参考数据，所以 Windows 版永远只能是 `A0-W`，不能升级成 A0，后面所有实验的基准都是悬的。

试着找参考端：WSL 命令在，但还没装发行版。讨论下来，三个落地方式里我选了最彻底的那个——WSL2 成为 A0 到 A4 的主实验环境，原版依赖、训练、推理、评测全在同一个 Linux/CUDA 后端跑；Windows 只负责代码管理、任务调度和论文可视化。原来的 Windows pilot 降级为兼容性证据，不再作为论文主基准。A0 冻结失败就禁止启动后续阶段，也不允许 WSL 出问题后静默回退到 Windows 后端。

这份架构规范已经写好提交，详细实施计划也拆成了可验证的小步骤，包括 WSL2 安装、原版依赖部署、A0 冻结门槛、单序列验收和完整序列扩展。今天到这里为止，环境和代码都还没动——下一步是先决定执行方式，再动手装。

## 今日要点

- 在 Windows 上完成了 MM-Tracker 的纯 PyTorch 兼容后端，118 个权重键严格加载，检测与运动场缓存全链路跑通，并建立了带哈希的运行清单与事件记录。
- 独立审查抓出运动场位移单位差约 14 倍的错误，修正后重算全部真实证据；最终单序列 pilot 指标为 HOTA 67.32、IDF1 79.40、MOTA 63.89。
- 单序列结论保持"结论不明"：只有约四成情况 Motion Mamba 胜过卡尔曼滤波，oracle 上界仅 +1.97 个百分点，所有正 alpha 未带来提升，A2 及后续阶段暂不启动。
- 架构改为 WSL2 做主实验环境，Windows 退为管理与可视化端；Windows 结果严格保留为 A0-W，跨平台三层一致性验证通过前不得成为论文基准。
