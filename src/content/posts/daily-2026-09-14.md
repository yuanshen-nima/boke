## 我差点把自己的 GRU 当成官方 DP

被问"PlugTrack 用的是数据驱动模型，你这里用的是什么"时，才把这个混淆点摊开：本实验的 DP 是我们自己训的 Prob-GRU（输入 5 帧归一化窗口，输出 μ 和 σ²，Gaussian NLL + 抖动增广），KF 分支和融合模块才是官方原样。所以 val HOTA ~52 和论文里的 63.3 / 59.2 完全不可比——那是更重的 DP 堆出来的绝对值。

这个澄清很重要：论文的比较逻辑必须写成"同一个 DP 下，加不加 U_DP 有没有增益"，而不是绝对值竞赛。想升级主张，就得把 DP 换成官方的，验证 U_DP 跨 DP 通用。

## 换官方 DP：从 TrackSSM 转向 DiffMOT

一开始我推 TrackSSM，理由是跟之前 mamba 的经验最近。读完官方接入模板后改判，DiffMOT 有三个决定性优势：

1. **没有编译风险**——图编码器 + Transformer 去噪网络 + 线性 variance schedule，纯 PyTorch；TrackSSM 的 mamba 选择扫描核才是 Windows 的坑。
2. **接口同构**——它对宿主的输入输出约定和我们现有 FusionRuntime 几乎一一对应。
3. **不确定性几乎免费**——`sample()` 是单步采样器，一次抽 K 个候选，用 K 个采样的方差当 U_DP，成本极低。

贵的东西都能复用：检测缓存（val + test）、B0-KF 结果、融合框架、评估打包工具链，全都不用重跑。真正要做的只有 vendor 代码、下权重、封装 Runtime、冒烟、融合重训、val 四组、test 四组，估一个工作日。最大的不确定项是权重托管在网盘上，有配额风险。

## 一个需要拍板的语义问题

换成 DiffMOT 后，E3 的故事会变：U_DP 从"异方差 NLL 学出来的 σ²"变成"扩散模型自身采样的分布方差"。两者都是"DP 自己的不确定性"，但论文表述得跟着改——大意是随机预测器的采样多样性本身就是预测不确定性，我们首次把它显式接进融合，和 KF 的 NIS 不确定性对等使用。这反而让"为什么以前没人用 DP 的不确定性"更好回答：信息一直都在，只是没人接。
