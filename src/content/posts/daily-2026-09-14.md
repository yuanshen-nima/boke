今天的主线是给 batetracker 收尾 DanceTrack 的 test 集，顺带把"要不要换成官方数据驱动预测器"这件事想清楚了。原本以为跑完 test 就能看到指标，结果先被一个常识拦了一下：test 的 GT 不公开，本地根本算不了 HOTA/AssA 那一套。于是这一天的重点变成了"把推理跑完、把提交件做对"，以及为下一步的 DP 替换做规划。

## test 集跑完：本地只负责推理，指标交给官方服务器

DanceTrack test 有 35 个序列，解压后确认没有 GT 目录，符合预期。我的流程是：先把检测缓存单独封存，四组方法共用同一份缓存（35 序列、29 万多条检测，带 SHA256 manifest），再分别跑 B0-KF、B1-ProbGRU、E2-PlugTrack、E3-DualU。四组最终都是 35/35 完成，用的还是 val 阶段那套抖动增广 GRU 加 v2 融合权重，checkpoint 没有换。

中间有个小插曲：链路"完成"得太快，我第一反应是不可能，四组跟踪不可能十几分钟结束。翻日志发现其实全部成功——之前在 val 阶段机器上缓存构建、训练、多运行并行，CPU 争抢严重；现在机器空载，速度回到正常水平。这提醒我，同一套流程在负载不同时耗时能差一个数量级，看进度不能只看时间。

指标这边只能按官方流程走：打包成 CodaBench 提交件，zip 内是 `tracker/` 加 35 个序列 txt，十列格式（帧、id、x、y、w、h、conf、-1、-1、-1），已和官方模板比对过。

## 自动编排很好用，但打包脚本静默失败了

为了不反复轮询缓存进度，我把后半段全链路自动化了：等 manifest 落盘，自动并行跑四组 test，评估完成度并打包。结果四组都跑完了，zip 却没产出。手动执行打包脚本才发现，脚本里引用的还是旧目录名，失败时没有任何报错。补齐目录名后打包成功，格式验证也通过。

结论是：编排脚本本身省了不少时间，但"静默失败"比"直接报错"更危险。以后这类脚本至少要在关键产物处做存在性断言，而不是只看退出码。

## 澄清一个误会：我的数据驱动预测器不是 ByteTrack

回看结果时我追问了一句：PlugTrack 用的是数据驱动模型，这个实验里到底用的是什么？答案是本项目自己训练的 Prob-GRU，不是 ByteTrack。ByteTrack 在这个体系里是关联和生命周期的宿主，检测器用的是官方 YOLOX-X DanceTrack 权重，KF 分支和融合模块都是官方资产原样接入。真正替换掉的是官方 PlugTrack 里的 DP——官方用 TrackSSM 或 DiffMOT，我用 GRU，因为 V1.2 计划要求 DP 能输出 μ 和 log σ²，而官方那两个是确定性的、没有方差头。

## 换成官方 DP 要重跑多少：先分层，再反转

接着评估"换官方 DP 再加 U_DP 分支"的成本。结论是分层很清楚：检测缓存、B0-KF、融合框架、评估与打包工具链都能直接复用；必须重做的是官方 DP 的环境与权重获取、给它加 log-var 头并在 train 上微调、重训 E2'/E3' 融合、重跑 B1'/E2'/E3' 的 val 和 test，最后补 sanity 检查。大头在前两步，顺利一天内，遇到环境问题可能两三天。

原本更担心 TrackSSM 的 mamba CUDA 核在 Windows 上的适配，倾向先做它。但读完官方接入模板后判断反转了：DiffMOT 是纯 PyTorch 的图编码器加 Transformer 去噪，没有自定义 CUDA 核，适配风险几乎为零；接口也和现有管线同构，同样是 (B,5,8) 条件窗口、残差式输出、同一套 CME/ABG/KF，对我而言基本就是把 `ProbGRURuntime` 换成 `DiffMOTRuntime`。更妙的是它的 `sample()` 是单步采样器，一次返回 K 个候选，用 K 个样本的方差来做 U_DP 非常便宜。

调研代理中途超额，我索性自己去读了 DiffMOT 仓库的关键文件，把采样器、编码器定义和 checkpoint 格式都确认了一遍，执行计划已经写出来，明天可以直接动手。

## 今日要点
