今天的主线只有一件事：把 batetracker 拉到 DanceTrack 的 test 集上跑完整流程。本来以为"跑一下测试集"是个下午就能收尾的活儿，结果一开始就被一个硬事实拦住了——test 的标注压根不公开，本地能做的和不能做的必须提前分清。

## DanceTrack test 没有公开 GT

这是我今天最有价值的一个认知纠正。我原本的直觉是：验证集怎么跑，测试集就怎么跑，顺手把指标一算就完事。但 DanceTrack 的官方流程不是这样——test 集只给你视频，不给你标注，本地算不出任何跟踪指标。想要数字，唯一的路径是把跟踪结果按官方格式打包，提交到 CodaBench 服务器上去评测。

这意味着"跑测试集"这件事应该被拆成两段：一段是我能在本地控制的，也就是推理和产物打包；另一段是提交之后等服务器返回结果，中间是个黑盒。想清楚这一点之后，整个执行计划才站得住，否则很容易在"为什么算不出 MOTA"上白耗时间。

## 这一轮我给自己排的四个动作

明确了边界，接下来就是工程活儿。我把这一轮拆成了四步：

第一，解压 test 集。这次一共 35 个序列，数量比验证集少，但每条序列的时长和拥挤程度都不低，解压本身也不快，所以我直接丢到后台去了。

第二，把检测缓存封存好。这是上一轮踩过坑的地方——检测阶段是整个流水线里最贵的一步，如果中途因为配置改动导致缓存失效重跑，一晚上的时间就没了。所以我的原则是：test 这一轮的检测缓存一旦建好就锁住，后续所有方法都复用同一份，不再动。

第三，四组方法在完整 test 上全量跑一遍。我手头这四组配置在验证集上已经各自跑通过，这次要在 test 上原样重放，尽量不引入新的变量。

第四，打包成 CodaBench 能认的提交件。格式必须严格贴合官方要求，序列命名、结果文件的组织方式都不能出错，否则提交上去直接被拒，来回沟通的成本比打包本身高得多。

## 配置隔离这件小事

计划定下来之后，第一个动手的细节是配置文件的隔离。

之前验证集的配置里带了 run_id，如果 test 直接复用同一套配置，产物会往同一个命名空间里写。轻则日志混在一起难排查，重则缓存被覆盖——尤其是检测缓存这种"命中即省一晚上"的东西，绝对不能冒这个险。所以我的做法是给 test 起一套独立的配置，run_id 统一加上 `-test` 后缀，让验证集和测试集的产物从命名上就彻底分开，互不干扰。

这个改动本身很小，但我越来越觉得这类"命名空间隔离"是长跑项目里最便宜的保险。花五分钟改个后缀，省掉的是半夜起来排查"为什么结果对不上"的一两个小时。

## 顺手把打包脚本写了

和配置一起准备好的还有 CodaBench 的打包脚本。

打包这件事的特点是：逻辑简单但要求严格，而且一旦出错就是全量返工。所以我没有等到四组方法都跑完再临时拼脚本，而是提前写好，让它在推理跑完的那一刻就能一键出包。脚本要做的事情大致是把每个序列的跟踪结果按官方命名的规则整理好，再压成符合提交要求的压缩包。

提前写的另一个好处是，我可以在只有一两个序列结果的时候先做一次格式自检，确认打包链路是通的，而不是等所有序列跑完才发现格式不对——那时候再回头改，成本又上去了。

## 目前的进度

解压已经跑完了，35 个序列齐了，目录里没有 GT 文件夹——这完全符合预期，反倒是再次确认了前面那个判断：本地确实没有可算的指标。紧接着我启动了 test 的检测缓存构建。

这条链路一旦开始，就是纯粹等时间了。检测缓存建好之后，四组方法可以并行推，然后走打包、提交。遗留的问题主要有两个：一是 CodaBench 的提交件格式我目前只是按文档理解，真正上传前还想再核对一遍细节；二是四组方法全量跑完之后，到底哪一组在 test 上更有竞争力，本地给不了答案，必须等服务器返回评测结果。所以今天晚上能拿到的只是"产物就绪"，不是"结论就绪"。

## 今日要点

- DanceTrack test 的标注不公开，本地算不出任何指标，唯一路径是打包提交到 CodaBench，这个流程边界必须先明确再动手。
- 这一轮的执行链是：解压 35 个 test 序列 → 封存并复用同一份检测缓存 → 四组方法全量推理 → 打包成提交件，检测缓存绝不允许重跑。
- 用 run_id 加 `-test` 后缀把 test 与验证集的产物彻底隔离，避免日志混杂和缓存互相覆盖。
- CodaBench 打包脚本提前写好，并计划在部分结果就绪时先做一次格式自检，把返工风险前置消化。
- 进度停在"检测缓存构建中"；遗留事项是提交件格式的最终核对，以及四组方法在 test 上的真实排名——后者只能等服务器评测结果。
