今天一整天的重心都压在 MM-Tracker 的 WSL 复现上：从环境冻结、密封缓存到第一轮 replay 对照，一路挖到一个足以改写实验协议的架构事实。中间还穿插着把断更四天的博客同步链路彻底翻修，傍晚又开了个新坑。

## 把 MM-Tracker 钉死在 WSL 原版环境里

上午接着昨天的计划往下推。核心约束只有一条：A0 必须跑上游原版代码——原版入口、原版检测器、原版跟踪器、原版 CUDA 依赖，任何为 Windows 写的兼容模块都不许出现在执行路径上，而且要留下可写进论文的证据链。

Stage A 先把仓库关系理清：WSL 里那份 clone 看着有 84 行未提交改动，逐个文件比对后发现内容早已通过移植脚本提交到 Windows 主仓，逐字节一致，属于陈旧副本，直接归档。随后把工作分支推到 GitHub，把两个创新点参考仓（PlugTrack 的融合模块、OC-SORT 的 OCM/ORU）clone 到 WSL 的 ext4 上备用。

数据侧做了件让我踏实的事：把本地 val 的 2846 帧逐帧哈希，再和官方 zip 的中央目录清单比对，得到 `matches_official_split: True`。也就是说手上这份 val 就是官方完整 split，只不过只有 7 个序列——低于确认性分层要求的 8 序列门槛。这个结论已经写进预注册说明，不假装它是 full-val。

环境冻结前补装了 tkinter、motmetrics、tensorboard，并把 pip-freeze 重新导出存证。preflight 汇总最后 7/7 全过。

## 一个协议级发现：KF 和 Motion Mamba 从不同时活跃

这是今天最重要的收获。为了让 R0 能同时记录 KF 预测和 MM 预测，我把上游三个 tracker 候选逐个读完，结论出乎意料：

- 官方评估脚本默认用的 `MCByteTrackerBias` 是**纯 Motion Mamba**——预测等于上一帧框加上 flow 场在框中心的采样偏移，KF 的 predict/update 全被注释掉；
- `--no_bias` 的 `MCByteTracker` 是**纯 KF**，flow 收下了但根本没用。

也就是说，这个仓库发布的代码里，KF 与 MM 从来没有同时活跃过。这反过来印证了论文的方法定位——Motion Mamba 是来**替代**卡尔曼滤波的。另外确认了 Motion Mamba 的真实角色：它是帧间特征级运动估计器，输入连续两帧的 FPN 特征、输出稠密 flow 场，所以密封缓存必须缓存每帧特征加检测输出，A0 和后续变体都从缓存重放。

对应方案是"影子 KF"：instrumented 运行时平行跑一套上游自带的 KF 状态，只记录不参与任何关联决策，输出的 MOT 文件必须与无观测运行逐字节一致——这正是等价门要证明的东西。

## 环境级兼容：numpy 别名与 cudnn 确定性

真正跑起来才暴露出两个经典坑，而且都不能改上游干净树：

一是 numpy 2.x 移除了 `np.float` 这类别名，而上游匹配模块里有 19 处在运行时用到。降级会炸掉整个锁定栈，改上游又违反零污染。最后做成环境级 shim（仓库内保留 canonical 副本，经 PYTHONPATH 生效），并把废弃别名全量扫了一遍。

二是 live E2E 与 replay 的第一层逐字节对比在第 4 行就挂了：同一检测、同一分数，框宽只差 0.1。定性后是 `cudnn.benchmark=True` 让每个进程 autotune 选了不同卷积算法，低比特差异被后处理放大。修法同样走环境 shim，把 cudnn 钉死在 deterministic 模式，缓存构建、live、replay 三方统一算法选择。

顺带还踩了两个小坑：跨 wsl.exe 的内联命令里 `$var` 和 `$()` 会在 Windows 侧被提前展开或清空，规则改成全字面量、复杂逻辑写脚本文件；以及检查点门跑完在干净树里留下 38 个 untracked pyc——清掉之后又误删了作者自己提交的 tracked pyc，恢复后加 `PYTHONDONTWRITEBYTECODE=1` 重跑。

Stage D 的密封缓存最终建成：2846 帧、26.7GB、全文件哈希密封，而且是开着一个可见窗口跑的，训练和推理过程我全程能盯着。

## 博客断更四天的排查

中午发现日报连续几天没上线，排查下来是三个独立问题叠加：9-07 那天深夜电脑没开机，计划任务直接错过；9-08 日报其实生成了，但推送时连接被重置，文章卡在本地；9-09 脚本崩了——我之前写的时间戳解析有 bug，切片长度错了，那天恰好第一次出现 Codex 会话就炸了。9-10、9-11 则是确实没对话，正常跳过，不发空文章是对的。

顺手发现机器上那个监听的代理端口其实完全没有转发能力，连普通站点都过不去，所以深夜任务根本没有可用通道。既然网络是间歇性的，就把它改成自愈模式：解析改走会话元数据时间戳、推送失败后自动依次尝试直连和几个常见本地代理端口、每次运行先补推积压提交，另外新增一个每天早上的补推任务兜底。LLM 调用侧也加固了重试，之前有一类断流异常没被捕获。最后积压的四篇日报全部推送上线。

## 开一个新坑：UAV ByteTrack 可靠性

傍晚起了个新项目。目录还是空的，侦察结果：数据集三个完整 zip 都躺在旁边没解压，旧的 val 只解了 7 个序列；全盘没有 VisDrone 检测器 checkpoint，旧项目那份单序列 smoke cache 没有检测器溯源信息，不能当 authoritative cache，得重新建一次冻结缓存。系统默认 Python 3.14 太新，好在旧项目留了 conda 环境说明可以复用。确认完这些就直接开工了。
