今天主要做了两件事：上午把 MOT17/MOT20 的完整 test 推理跑完，下午转去复现 TrackSSM，并把自己的改进模块接上去做对照。两边都得出了结论，但都不是"指标涨了"这么简单——一个是拿不到分数，一个是涨幅小到还不能下结论。

## MOT test：跑完了，但没有分数

MOTChallenge 的提交和在线评测服务已经关停，MOT17、MOT20 的页面都成了静态归档，排行榜停留在四月的状态。我核对了官方发布的标签包，里面只有 train 的 GT，没有 test 的 GT，本地数据包同样如此。所以"上传结果换 HOTA"这条老路走不通：能生成测试集轨迹、能测速度，但算不出 test 上的 HOTA、IDF1、MOTA。

既然如此，我把这次的任务定成两件事：一是走通完整的 test 推理链路，产出可追溯的轨迹；二是把所有运行测量记录清楚，方便以后有了合法评分渠道再做验证。论文里的评测证据，则改用已有的 DanceTrack 官方 test 结果做主要支撑，MOT17/MOT20 继续用本地 half-val 做补充对比。

## 让这次推理尽可能干净

为了不让"结果看起来不错"变成"流程没跑对"，我加了几道约束。

首先，test 的输入和推理单独开入口，不动原来的 half-val 脚本和产物，输出统一标注为"test 推理、无本地评分标签"，并显式跳过 TrackEval，避免把不可评分的结果误报成指标。其次，四组方法共用同一套检测和 Re-ID 特征，保证配对条件一致；每个 run 都记录帧覆盖、输出行数、结果哈希和权重路径。

跑起来后还发现一个可以省掉大量重复工作的地方：MOT17 的 21 个条目其实是 7 段视频各带三种检测器后缀。我先逐帧比对后缀序列的图像字节，只有完全相同才复用检测与 Re-ID 缓存。MOT17-03、06、07 都通过了逐帧哈希校验，最终 14 个 FRCNN/SDP 序列复用了 DPM 的缓存；一旦某帧不一致就退回独立生成，不做强行复用。

最终八个 run 全部完成：MOT17 覆盖 21 个序列、17,757 帧，MOT20 覆盖 4 个序列、4,479 帧。跟踪帧率大致在 MOT17 B0 的 78.7 FPS 到 MOT20 E1 的 37.1 FPS 之间，MOT20 高密度序列的峰值显存约 228 MiB，其余基本在 100 MiB 左右。这些数字都是 tracker 子进程的端到端耗时，不含前置的检测和特征生成——那段才是真正慢的部分，MOT20-04 只有 3 FPS 上下。

## TrackSSM：先把基线复现干净

下午换到 TrackSSM。作者的代码和运动模型权重都已公开，但要跑在本机并不轻松：本机是 RTX 5060 Ti，属于 Blackwell，PyTorch 要到 2.7/CUDA 12.8 才有支持，而作者指定的是 PyTorch 2.0.1/CUDA 11.8 加一套较老的 Mamba 依赖。我保留了官方的模型、权重和算法，只做硬件相关的环境适配，并把环境差异单独记录。

有一个细节值得一提：官方配置里名为 test 的 yaml 实际指向 val，代码里权重和评估路径也有硬编码。我逐项核对后确认了这一点，并按论文口径固定训练轮数为 120（仓库里写的是 800，与论文不一致，这里按论文走）。

复现结果对得上：DanceTrack val 25 个序列、25,508 帧全部跑完，HOTA 53.795、AssA 36.847、IDF1 53.726，按论文的一位小数精度就是 53.8 / 36.8 / 53.7，与论文表格一致。论文里的 57.7 是 test 结果，两者分开记录。

## 把改进接到 TrackSSM 上

在基线上接入我的三件套：PlugTrack LSTM 融合、可靠性比修正、NIS residual，三组顺序对照。可靠性统计重新在训练集内部的 fit/dev 划分上估计，NIS 适配器只训练新增的约一万七千个参数，原运动模型和 CME/ABG 全部冻结，零适配器的输出与修正基线的最大差异在 6e-8 量级，属于浮点误差。

四组结果如下：原 TrackSSM 53.7952，加上作者 PlugTrack 融合降到 53.7441，再加可靠性修正回到 53.8202，再加 NIS residual 到 53.8372。完整组合相对原 TrackSSM 只涨了 0.042 个百分点，而且 AssA 和 IDF1 都没超过原版。也就是说，增益存在但很小，还不能称为稳定提升。

## PlugTrack 为什么会掉点

最有意思的是诊断过程。先把下降拆到序列上：25 个 val 序列里 9 升 16 降，个别序列波动很大，说明汇总值掩盖了分布差异。继续回放定位到一条具体路径：某序列第 155 帧，融合预测让一条丢失轨迹与另一条活动轨迹的 IoU 从 0.811 升到 0.902，跨过了 BYTETracker 的 0.85 去重阈值，旧 ID 被提前删除；到第 158 帧检测再次出现时，原版能恢复旧 ID，融合组只能新建一个 ID。融合框"平均更准"了，却在离散决策阈值上踩了坑，这类影响不会出现在平均 IoU 里。

但我做了两轮反事实对照后，发现这解释不了整体下降：关掉去重后，PlugTrack 的 HOTA 反而从 53.7441 掉到 53.6986，原 TrackSSM 也略降；那处局部故障虽然修好了，整体却更差。另一个发现是配置差异的实质影响——采用上游验证配置的低分阈值 0.4 后，原 TrackSSM 直接升到 54.6931，同配置下 PlugTrack 是 54.1283，仍差约 0.565。

所以目前的准确结论是：当前公开权重接入后，在两种配置下都出现了下降，而且我没找到能修复它的单一接入错误；但这不等于 PlugTrack 无法带来提升。下一步更值得做的是按论文流程重新训练 CME/ABG，重点验证"公开融合权重学到的策略，和当前跟踪器实际产生的历史与关联过程是否匹配"。在跑通之前，这个基线我会标成"复现未对齐、下降原因未解决"，而不是"无提升"。

## 今日要点

- MOT17/MOT20 的 test 推理已完整跑通：8 个 run、21+4 个序列、共 22,236 帧，轨迹与运行测量齐全，但因为官方评测关停且没有 test GT，没有产生任何 test 分数。
- 推理流程做了后缀图像哈希校验复用、断点续跑和配对输入三项优化，14 个 MOT17 后缀序列复用了检测与 Re-ID 缓存。
- TrackSSM 在适配新硬件环境后复现成功，DanceTrack val 的 HOTA/AssA/IDF1 与论文一位小数精度一致。
- 我的改进接上 TrackSSM 后只有 0.042 HOTA 的增量，AssA 和 IDF1 反而略低于原版，暂时按"小增益、未证实"记录。
- PlugTrack 的下降已定位到一处去重误删，但消融说明它不是整体原因；低分阈值 0.4 与 0.1 的差异对指标影响明显，后续报告必须分协议记录。
